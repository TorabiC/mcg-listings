# metrics.json schema additions (2026-07-30)

This documents the fields `bin/collect.py` added to `data/<slug>/<period_id>/metrics.json`
for the harvest-freshness guard, weekly/monthly rollup, and Clarity adapter
work, for the mcg-marketing-hub app (or anything else) reading these files
directly. Every field below is additive -- nothing pre-existing was renamed
or removed, so older consumers keep working unchanged. See `README.md` for
the full pipeline; this file is the field-level contract for the new parts.

## `source_freshness` (top-level, all period types)

```json
"source_freshness": {
  "<source_key>": {
    "as_of": "2026-07-27" | null,
    "status": "fresh" | "stale" | "missing"
  }
}
```

- **Keys**: `idx`, `cc`, `ga4`, `tawk`, `homes.com`, `crexi`, `loopnet`,
  `clarity`. Note this is keyed by individual portal (`homes.com` /
  `crexi` / `loopnet`), not the combined `portals` block that
  `data_quality` uses -- freshness is meaningful per-portal since each
  portal's snapshot file is refreshed independently.
- **`fresh`**: the number on the page is current for this reporting
  period -- either a live API pull made this run (idx/cc/ga4/tawk), or a
  portal snapshot whose `harvested_at` falls on/after the period start.
- **`stale`**: real data, just not captured inside this window -- a
  portal snapshot file exists but its `harvested_at` predates the period
  start, or has no `harvested_at` at all (tolerated, but never assumed
  fresh without proof). The report shows a visible "as of {date}" caption
  (or a generic "most recent snapshot on file" caption when `as_of` is
  null) rather than presenting it as current-period activity.
- **`missing`**: no data at all for this source this period (matches
  `data_quality`'s "missing" for that source).
- **`clarity`** carries one extra field, `coverage_days` (int): how many
  of the requested window's days the Clarity live-insights pull actually
  covered (API-capped at 3). `status` is `"fresh"` only when
  `coverage_days` reaches the full period length; otherwise `"stale"`
  even though the data is real and recent, so it's never treated as a
  primary/period-complete view count.

## `period_activity` (weekly metrics.json only)

```json
"period_activity": {
  "homes.com": { "views": 37 | null, "saves": 2 | null, "has_baseline": true, "baseline_period_id": "2026-W30" | null },
  "crexi":     { "views": 0 | null,  "leads": 0 | null,  "has_baseline": true, "baseline_period_id": "..." },
  "loopnet":   { "views": 0 | null,  "leads": 0 | null,  "has_baseline": true, "baseline_period_id": "..." }
}
```

Portal counters in `sources.portals.<portal>` are cumulative-since-listing
(portal dashboards don't expose historical per-week numbers). `period_activity`
is this period's *delta* against the nearest prior period's stored
metrics.json (walking back up to 3 periods to bridge a gap), floored at 0.
When no prior baseline exists at all (`has_baseline: false`), every field is
`null` -- render copy as "total since listing," never "this week," when you
see a null here.

## `weekly_breakdown` / `missing_weeks` (monthly + quarterly metrics.json only)

```json
"weekly_breakdown": [
  {
    "week_id": "2026-W27",
    "start": "2026-06-29", "end": "2026-07-05",
    "total_views": 187, "total_leads": 2,
    "portals": {
      "homes.com": { "views": 37 | null, "saves": 2 | null },
      "crexi": { "views": 0 | null, "leads": 0 | null },
      "loopnet": { "views": 0 | null, "leads": 0 | null }
    }
  }
],
"missing_weeks": ["2026-W28"]
```

- One row per ISO week overlapping the month/quarter window that has a
  stored weekly `metrics.json` on disk. `total_views`/`total_leads` are
  read straight from that week's own `sources` block (same figure the
  weekly report itself showed); `portals.*` mirrors that week's
  `period_activity` deltas.
- `missing_weeks`: ISO week ids overlapping the window with **no** stored
  weekly metrics.json -- excluded from every total (`period_activity`,
  `weekly_breakdown` sums) rather than estimated or assumed zero. Render
  this list transparently (the "Month in review" report section does) so
  a gap in collection is visible rather than silently absorbed into the
  totals.
- The monthly/quarterly `period_activity` block (top-level, same shape as
  the weekly one above) is the SUM of every included week's per-portal
  deltas, with `has_baseline` true only if at least one constituent week
  had a baseline, and an added `weeks_included` (int) count instead of a
  single `baseline_period_id`.
- Quarterly metrics.json is generated by the exact same code path as
  monthly (`build_rollup_metrics` / `iso_weeks_overlapping` in
  collect.py) over a wider `[start, end]` window -- no schema difference
  between the two beyond however many weeks/rows that produces.

## `data_quality` (existing field, now includes `clarity`)

Unchanged shape (`{"<source>": "live" | "sample" | "missing"}`), with one
new key: `clarity`. Note `data_quality` is keyed by the combined `portals`
block (one status covering homes.com+crexi+loopnet together), while
`source_freshness` is keyed per-individual-portal -- check `data_quality`
for "did we get portal data at all this period" and `source_freshness` for
"is any given portal's number current."

## `sources.clarity` (new source block, all period types)

```json
"sources": {
  "clarity": {
    "sessions": 30, "engaged_sessions": 9, "distinct_users": 21,
    "coverage_days": 3,
    "note": "reflects only the most recent 3 day(s); Clarity's live-insights export can't cover a full 7-day window" | null
  }
}
```

Supplemental engagement signal only -- never summed into `total_views` /
`aggregate_totals()`, and never rendered as its own vendor-named channel in
the report (folded into "MCG website analytics" alongside GA4). `note` is
non-null whenever `coverage_days` is less than the full period length.

## `sources.cc.email_campaigns_to_date` (new field, existing `sources.cc` block)

```json
"sources": {
  "cc": {
    "campaigns": [ { "...": "...", "sent_date": "2026-07-29" } ],
    "totals": { "sent": 400, "opens": 120, "clicks": 18 },
    "email_campaigns_to_date": { "campaigns": 2, "sends": 900, "opens": 240, "clicks": 40 }
  }
}
```

`campaigns`/`totals` now only include campaigns whose resolved send/update
date falls inside the reporting window (see CCAdapter period-scoping fix).
Every matched campaign sent/updated *before* the window rolls into
`email_campaigns_to_date` instead -- a separate cumulative counter, never
added into `totals`, so a listing's original announcement send from weeks
ago can't reappear as this week's send count.
